The Tuteliq API provides AI-powered child safety detection across text, voice, images, and video. This page covers everything you need to know before making your first call.

## Base URL

```
https://api.tuteliq.ai/api/v1
```

All endpoints are prefixed with `/api/v1`. For example, the bullying detection endpoint is at:

```
POST https://api.tuteliq.ai/api/v1/safety/bullying
```

## Authentication

Include your API key in every request using one of these methods:

<CodeGroup>
```bash Bearer Token (Recommended)
curl -X POST https://api.tuteliq.ai/api/v1/safety/bullying \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "message to analyze"}'
```

```bash API Key Header
curl -X POST https://api.tuteliq.ai/api/v1/safety/bullying \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "message to analyze"}'
```
</CodeGroup>

Get your API key from the [Tuteliq Dashboard](https://tuteliq.ai/dashboard).

## Response Format

### Successful response

There are two response shapes, and which one you get depends on the endpoint family.
Both carry `confidence`, `risk_score`, `rationale`, `recommended_action`, `language`,
`language_status` and `credits_used`. They differ in how they name the verdict and how
they express severity, so read this before writing a shared parser.

<Warning>
`severity` means different things in the two families. In the core safety family it is an
enum; in the fraud and extended-harm family it is a number from 0 to 1, and the enum is
called `level`. Branch on `recommended_action` and you sidestep the difference entirely.
</Warning>

**Core safety family** — `/safety/bullying`, `/safety/unsafe`, `/safety/grooming`.
Each names its own verdict field and returns a flat category vocabulary.

```json
{
  "is_bullying": true,
  "bullying_type": ["verbal_abuse", "exclusion"],
  "severity": "high",
  "risk_score": 0.85,
  "confidence": 0.92,
  "speaker_role": "enacting",
  "rationale": "Direct insults combined with social exclusion targeting a 10-12 year old.",
  "recommended_action": "flag_for_review",
  "action_detail": "Route to a moderator. The exclusion pattern suggests a group dynamic worth reviewing beyond this single message.",
  "language": "en",
  "language_status": "stable",
  "credits_used": 1
}
```

`/safety/unsafe` returns `unsafe` and `categories` in place of `is_bullying` and
`bullying_type`. `/safety/grooming` returns `grooming_risk`, `flags` and a per-message
`message_analysis` array; see [Grooming detection](/grooming-detection).

**Fraud and extended-harm family** — `/fraud/*` and the extended `/safety/*` endpoints
(`coercive-control`, `tfgbv`, `radicalisation`, `gambling-harm`,
`vulnerability-exploitation`, `distress-signals`). These share one shape, identified by
the `endpoint` field, and carry evidence excerpts.

```json
{
  "endpoint": "romance-scam",
  "detected": true,
  "level": "high",
  "severity": 0.78,
  "confidence": 0.92,
  "risk_score": 0.85,
  "categories": [
    { "tag": "URGENCY_FABRICATION", "label": "Fabricated Urgency", "confidence": 0.95 },
    { "tag": "FINANCIAL_REQUEST", "label": "Financial Request", "confidence": 0.88 }
  ],
  "evidence": [
    { "text": "I only need 4,000 to release it", "tactic": "FINANCIAL_REQUEST", "weight": 0.88 }
  ],
  "age_calibration": { "applied": true, "age_group": "10-12", "multiplier": 1.3 },
  "recommended_action": "flag_for_review",
  "rationale": "A financial request paired with fabricated urgency and an unverifiable absence.",
  "credits_used": 1
}
```

Whichever family you are in, `recommended_action` is the field to branch on. It is a
stable enum, weakest to strongest: `none`, `monitor`, `flag_for_review`, `block`,
`immediate_intervention`. Prefer it to the verdict boolean, which fires at any severity
including low-severity cases you probably only want to log.

### Response marks

When a step after the analysis changes a result, the response carries a mark that says so.
Each mark is a boolean named for what happened (`..._raised`, `..._capped`, `..._watched`,
`..._cleared`), with a `..._reason` string beside it that explains it in plain language. A
mark is absent unless it applied, and `recommended_action` already includes its effect, so
you never need to branch on a mark to route correctly. Marks are there so a reviewer can
see why a result landed where it did.

| Mark | Endpoints | What it means |
|------|-----------|---------------|
| `no_harmful_act_capped` | `/fraud/social-engineering`, `/fraud/app-fraud`, `/fraud/romance-scam`, `/fraud/mule-recruitment`, `/safety/gambling-harm` | A review that rested on the topic alone was brought down to `monitor`, because none of the acts the detector looks for is in the text: nothing asked of the reader, no pressure, secrecy or move somewhere private, no lure, and nobody telling of harm happening now. `detected`, the level and the categories are as the analysis gave them. Never applied when a minor is declared. |
| `no_harmful_act_urgency_capped` | Same five endpoints | An urgent result with none of those acts in the text is brought down to `flag_for_review`, not to `block`, so a person still sees it before anything is withheld. It never goes lower than review. Never applied when a minor is declared. |
| `pressed_after_objection_watched` | `/safety/bullying` | One person objected and the other carried on, but what they carried on with was offered for the other person (help, company or concern), not at their cost and not mutual. It is not sent for review; the action is set to `monitor` so it stays visible. |
| `ordinary_hyperbole_capped` | `/safety/unsafe` | A review on compulsive use (alone, or with low mood) was lowered to `monitor` because the words exaggerate about an ordinary habit or an everyday pressure ("I'm addicted to this show", "exams are killing me") with no sign of real harm, distress or loss of control. Single messages only. Never applied for a declared minor, and never for substance use, self-harm or any other category. Categories, severity and score are unchanged, and it never clears to `none`. |
| `minor_on_adult_platform_raised` | Every endpoint that supports `minor_disclosure_check` | A speaker said they are under 18 on a platform that declared `dating` or `adult_community`, and a quiet result was raised to `flag_for_review`. See [Checking for a minor on an adult platform](#checking-for-a-minor-on-an-adult-platform). |
| `off_platform_raised` | `/fraud/romance-scam` | Somebody asks to move the conversation elsewhere **and** a second marker was found about the same person (see `off_platform_markers` below). A result below review is raised to `flag_for_review`, and a review is held there. Never raised higher, and never in a setting where harm is discussed. |

Romance scam also returns a descriptive field that changes nothing on its own:

| Field | Type | Description |
|-------|------|-------------|
| `off_platform_request` | boolean | `true` when somebody in the text asks, suggests or presses to continue the conversation somewhere else (another app, a phone number, an email address or another private channel); `false` when nobody does. On its own it never changes the action: people who get on often move. Absent when it could not be determined, and on a result lowered to nothing found. |
| `off_platform_request_reason` | string | Human-readable explanation, naming any second marker found. Present only when `off_platform_request` is `true`. |
| `off_platform_markers` | string[] | The second markers found about the person asking to move: `scam_persona` (abroad or far away for work, military, an oil rig or a ship, a mission or contract), `early_love_bombing` (love or lifelong devotion declared while the two barely know each other), `avoids_video_or_meeting` (refuses, dodges or puts off a video call or a meeting), `discredits_platform` (the reason for moving runs down the platform or its safety). Present only when `off_platform_request` is `true`; empty when there is none. |

Tuteliq does not keep `off_platform_request` against an account, so a platform that wants
to know how often one account tries to move conversations elsewhere can count `off_platform_request` across that
account's conversations on its own side.

The marks listed above are returned by the dedicated endpoints. `/analyse/multi` returns
`minor_disclosure`, `minor_on_adult_platform_raised`, `pressed_after_objection_watched` and
`ordinary_hyperbole_capped` in its per-detector results.

### Error response

Every error uses the same envelope, and `request_id` is the value to quote in a support
ticket:

```json
{
  "error": {
    "code": "AUTH_1001",
    "message": "API key is required. Include it as a Bearer token in the Authorization header or in the x-api-key header.",
    "request_id": "req_mu71meyo_ce663c02060d0914",
    "retryable": false,
    "status_url": "https://tuteliq.ai/status",
    "documentation_url": "https://docs.tuteliq.ai/error-handling#AUTH_1001"
  }
}
```

Retryable errors add `retry_after_ms` alongside a `Retry-After` header, and add
`degraded_components` when a dependency is the cause.

Rate limit rejections carry an upgrade path instead, and are the one case that does not
include `request_id`:

```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "You have exceeded your rate limit of 300 requests per minute.",
    "suggestion": "Upgrade to Assure for 5,000 requests per minute.",
    "details": {
      "tier": "build",
      "limit": 300,
      "window": "1 minute",
      "retry_after_seconds": 42
    },
    "links": {
      "upgrade": "https://tuteliq.ai/dashboard/billing",
      "docs": "https://docs.tuteliq.ai/error-handling"
    }
  }
}
```

## Context Fields

Pass a `context` object with any detection request to improve accuracy:

```json
{
  "text": "message to analyze",
  "context": {
    "age_group": "13-15",
    "language": "en",
    "country": "GB",
    "platform": "Discord",
    "prior_messages": [
      { "role": "user", "text": "previous message" },
      { "role": "contact", "text": "response message" }
    ]
  }
}
```

`language` and `platform` are accepted on every detection endpoint. The rest are accepted
on most, and a few belong to one endpoint only. Where a field is not part of an
endpoint's schema it is ignored rather than rejected, so passing the full object
everywhere is safe.

| Field | Type | Description |
|-------|------|-------------|
| `language` | string | ISO 639-1 code (e.g., `"en"`, `"de"`, `"sv"`). Auto-detected if omitted. [32 languages supported](/languages). |
| `platform` | string | Platform name (e.g., `"Discord"`, `"Roblox"`, `"WhatsApp"`). Adjusts for platform-specific norms. |
| `age_group` | string | `"under 10"`, `"10-12"`, `"13-15"`, `"16-17"`, or `"under 18"`. Triggers age-calibrated severity scoring. `ageGroup` is accepted as a camelCase alias. |
| `prior_messages` | array | Prior turns of the conversation, oldest first. Each needs `role` and `text`, with an optional ISO 8601 `timestamp`. Request-scoped: nothing here is retained after the call. `conversation_history` is accepted as a legacy alias. |
| `country` | string | ISO 3166-1 alpha-2 code (e.g., `"GB"`, `"US"`, `"SE"`). Enables geo-localised crisis helpline data. Falls back to the account's country if omitted. |
| `conversation_type` | string | The setting the conversation was captured in, declared from your own platform configuration and never from end-user input. Honoured by every text detection endpoint: `/safety/bullying`, `/safety/grooming`, `/safety/unsafe`, `/safety/distress-signals`, `/safety/radicalisation`, `/safety/tfgbv`, `/safety/gambling-harm`, `/safety/coercive-control`, `/safety/vulnerability-exploitation`, `/fraud/social-engineering`, `/fraud/romance-scam`, `/fraud/app-fraud`, `/fraud/mule-recruitment` and `/analyse/multi`. Omit it and behaviour is unchanged; a value outside the supported list is rejected with a 400 that lists the supported values. See [Choosing a conversation setting](#choosing-a-conversation-setting) for what each setting does. |
| `minor_disclosure_check` | boolean | Optional, off unless `true`. For platforms whose users are adults and which suspect some users get past their age verification. Runs only when the request declares an adult. See [Checking for a minor on an adult platform](#checking-for-a-minor-on-an-adult-platform). |
| `sender_trust` | string | `"verified"`, `"trusted"`, or `"unknown"`. Verified senders suppress authority impersonation false positives. |
| `sender_name` | string | Sender identifier, used alongside `sender_trust` for impersonation scoring. |
| `relationship` | string | `/safety/bullying` only. Relationship between the participants, e.g. `"classmates"`. |

`/safety/grooming` does not take a flat `text` field and its context is different: pass
`messages` with a `sender_role` per turn, and use `context.child_age` and
`context.participant_age` rather than `age_group`. See [Grooming detection](/grooming-detection).

### Choosing a conversation setting

`context.conversation_type` tells the detectors where a conversation took place, so a
fraud desk transcript is not read as the fraud itself and a dating chat between adults is
not read as a chat with a child. Declare it from your platform configuration. You can also
set an account-wide `default_conversation_type`; whenever a setting is in effect, the
response names it in `conversation_type_in_effect` and says where it came from in
`conversation_type_source` (`request` or `account_default`).

| Group | Values | What it changes |
|-------|--------|-----------------|
| Where a person reports harm | `fraud_report`, `abuse_report`, `support_disclosure`, `helpline` | An urgent action is capped at `flag_for_review`, and `conversation_type_applied` comes back when that changed the action. A conversation in which the responsible party is already handling a person at risk, with nothing happening as the text is written, is kept at `monitor` and `protective_speech_capped` says so. Harm still going on is reported here, so it is still raised. |
| Where harm is discussed rather than happening | `clinical`, `investigative`, `legal`, `advisory`, `training`, `journalism`, `research` | Everything in the row above. In addition, raises that apply whatever is happening are not applied, because the harm is the subject of the conversation rather than something being done in it. On gambling harm, mule recruitment and romance scam, a high score on a result that asks for nothing is brought into the low band (`risk_score_lowered`) instead of being raised to review. Harm happening now still reaches review. |
| Moderation | `moderation_review` | An urgent action is capped at `flag_for_review`, as above. It is **not** a setting where harm is discussed: a moderator reviews content that may itself be the harm, so every raise still applies. |
| A professional or a responsible adult | `healthcare`, `law_enforcement`, `education`, `family` | A responsible party already handling a person at risk, with nothing happening as the text is written, is kept at `monitor`. Urgent actions are not capped. In `education` and `family` this applies only when the speaker is not the person at risk: a young person speaking for themselves alerts as with no setting. |
| A platform whose users are adults | `dating`, `adult_community`, `workplace` | See [Adult platforms](#adult-platforms) below. |
| Ordinary settings | `direct_message`, `group_chat`, `public_post`, `customer_service`, `gaming_chat` | Nothing. They let you be precise rather than leave the field blank. |

Three rules hold in every setting:

- **Harm being done is never excused.** Harm done in the conversation, by anyone
  including the responsible party, a person at risk with nobody acting, and anything acute
  alert as they would with no setting.
- **Harm happening now does not drop below review.** On social engineering, app fraud,
  romance scam, mule recruitment, gambling harm and bullying, harm happening now to the
  writer, or to a specific person the writer tells of, never ends below `flag_for_review`
  because of a setting. `ongoing_harm_floor_applied` says when that held a result.
- **A change is never silent.** When a setting changes a result, a response mark says so:
  `conversation_type_applied`, `protective_speech_capped`, `risk_score_lowered` or
  `ongoing_harm_floor_applied`, each with its reason where it has one.

#### Adult platforms

For an adult dating or social platform, declare `dating`. Use `adult_community` for an
age-gated adult community, and `workplace` for a workplace tool.

What `dating` and `adult_community` change:

- A willing conversation between adults, with no sign that anyone is under 18 and nobody
  pressured, is read as a conversation between adults. On `/safety/grooming` it is lowered
  with `adult_exchange_capped`; on `/safety/unsafe` an ordinary remark about adult life that
  shows no child is not sent for review (`no_child_shown_capped`).
- With [`minor_disclosure_check`](#checking-for-a-minor-on-an-adult-platform) turned on, a
  speaker who says they are under 18 raises a quiet result to `flag_for_review`.

What they do not change:

- No adult age is supplied to the detectors. Scams, coercion, threats, pressure and harm
  happening now are read exactly as with no setting, and urgent actions are not capped.
- A declared child beats the setting. A minor `age_group`, a child `sender_role` or a
  `child_age` under 18 removes the adult audience from the request, and so does a speaker
  stating an age under 18; `declared_age_overridden` tells you when that happened.

`workplace` behaves the same way for reading adults as adults, but a minor found in a
workplace conversation is reported without raising the result (see below).

### Checking for a minor on an adult platform

Some users get past age verification. Set `context.minor_disclosure_check` to `true` and
Tuteliq also checks whether a speaker says they are under 18, on a request that declares
an adult. It is off by default: omitted and `false` behave the same, and with it off
nothing about a response changes.

**When it runs.** Only when the request declares an adult and no child:

- an adult `age_group`, such as `"18+"` or `"adult"`;
- on `/safety/grooming`, `context.child_age` of 18 or over, or a `sender_age` of 18 or over
  on every message;
- or `conversation_type` `dating`, `adult_community` or `workplace`.

**What it recognises.** A speaker who states an age under 18, or says so in other words:
a school year, a parent's controls on their phone, a milestone such as being old enough to
drive, or a description of their daily life that is only true of a child.

**Where it is supported.** `/safety/bullying`, `/safety/grooming`, `/safety/unsafe`,
`/safety/distress-signals`, `/safety/radicalisation`, `/safety/tfgbv`,
`/safety/gambling-harm`, `/safety/coercive-control`, `/safety/vulnerability-exploitation`,
`/fraud/social-engineering`, `/fraud/romance-scam`, `/fraud/app-fraud`,
`/fraud/mule-recruitment` and `/analyse/multi`, where each detector's result carries the
fields.

**What a positive finding does.**

1. The declared adult age and the adult-audience setting are not used for this request,
   and `declared_age_overridden` is `true` with a `declared_age_overridden_reason`.
2. `minor_disclosure` describes the finding (fields below).
3. On `dating` or `adult_community`, a result that asked for `none` or `monitor` is raised
   to `flag_for_review`, with the level at `medium` and the score in the review band, and
   `minor_on_adult_platform_raised` is `true` with a reason naming the setting. A minor on
   an adults-only platform is the incident in itself. It is never raised higher, and a
   result already at review or above is left as it is.
4. On `workplace`, or with an adult age group and no setting, the finding is reported but
   nothing is raised. A 16- or 17-year-old can lawfully be at work, so a minor in a
   workplace conversation is not by itself a breach of the platform's terms.

**How this relates to `declared_age_overridden`.** A plainly stated minor age ("im 15")
has always dropped a declared adult age, with or without this option, and
`declared_age_overridden` reports it. With the option on, that case is also reported in
`minor_disclosure` (with `evidence_type` `stated_age`) and raised on `dating` or
`adult_community`, and minors who say it in other words are recognised as well.

| `minor_disclosure` field | Type | Description |
|-------|------|-------------|
| `detected` | boolean | Always `true` when the object is present. |
| `evidence_type` | string | What showed it: `stated_age`, `school_year`, `parental_control`, `age_milestone`, `life_stage` or `other`. |
| `message_index` | integer | 0-based index into the turns read: `prior_messages` first, oldest first, and the submitted message last. On `/safety/grooming`, the index into `messages`. |
| `suggested_age_group` | string | The value to send back as `context.age_group` on this user's later requests. Always a minor band: `under 18`, or `under 13`, `13-15` or `16-17` when the speaker stated an age. |
| `reason` | string | Human-readable explanation. It never quotes the message. |

`minor_disclosure` is absent when nothing was found, and never present on a request that
declared no adult.

```json
{
  "endpoint": "romance-scam",
  "detected": false,
  "level": "medium",
  "risk_score": 0.55,
  "recommended_action": "flag_for_review",
  "declared_age_overridden": true,
  "declared_age_overridden_reason": "The speaker says they are under 18, so the declared adult audience was not used.",
  "minor_disclosure": {
    "detected": true,
    "evidence_type": "school_year",
    "message_index": 2,
    "suggested_age_group": "under 18",
    "reason": "The speaker says in the latest message that they are under 18, by naming a school year that only children are in."
  },
  "minor_on_adult_platform_raised": true,
  "minor_on_adult_platform_raised_reason": "The platform declared an adult audience (conversation_type \"dating\"), and the speaker says they are under 18: a minor on an adults-only platform. Sent for review so a person can check the account.",
  "conversation_type_in_effect": "dating",
  "conversation_type_source": "request"
}
```

Tuteliq does not keep `minor_disclosure` or the suggested age group against the user; your
platform carries it forward to keep protecting them on later requests; see
[Carrying a signal forward](/composability#carrying-a-signal-forward).

<Note>
`minor_disclosure_check` is available on the REST API only for now. The MCP tools do not
expose it yet.
</Note>

### Carrying conversation state

There are two ways to give a detector the conversation rather than a single message, and
which you use depends on your call pattern.

Pass `context.prior_messages` when you already hold the whole thread and want it seen in
one call. Pass the `continuation_token` from the previous response when you are calling
once per new message as it arrives: the token carries derived trajectory state without
resending history, and without anything being stored server-side. See
[Continuation tokens](/continuation-tokens).

## Options

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `support_threshold` | string | `"high"` | Minimum severity to include crisis helplines. Values: `low`, `medium`, `high`, `critical`. Critical severity **always** includes support resources. |
| `verdict_only` | boolean | `false` | Fast mode. Skips generating `action_detail`, the moderator-facing expansion of `recommended_action`. The verdict itself (`severity`, `risk_score`, categories, `recommended_action`) and `rationale` are unchanged. See [Fast mode](/fast-mode). |
| `include_evidence` | boolean | `true` | Fraud and extended-harm endpoints. Include evidence excerpts with flagged phrases and weights. |
| `flag_profanity` | boolean | `false` | `/safety/bullying` and `/safety/unsafe`. Adds a deterministic word-list `profanity` block. Never affects the verdict, and costs no extra credits. |
| `flag_risk_terms` | boolean | `false` | `/safety/bullying` and `/safety/unsafe`. Adds a deterministic `risk_terms` block for bare drug and violence terms. Never affects the verdict. |

## Stateless by Design

Tuteliq is **fully stateless** — every API call is independent, and no conversation text, context, or session state is retained between requests. This is a deliberate **privacy-by-design** decision, not a missing feature.

**Why stateless?**

- **GDPR compliance** — Processing children's data under GDPR/COPPA demands the strictest data minimization. By retaining no cross-request state, there is zero risk of sensitive conversation data persisting in caches, logs, or backups.
- **No data retention surface** — There is no session store to breach, no conversation cache to leak, and no accumulated history to subpoena. Each request arrives, is analyzed, and the content is discarded.
- **Simpler compliance audits** — "We store nothing between requests" is the easiest privacy posture to audit and certify.

**What this means for developers:**

- Pass `context` (age_group, platform, language, conversation_history) with **every request** that needs it.
- Use `external_id` and `customer_id` to correlate results with your own systems — these are echoed back but not stored.
- If you need to track risk escalation across a conversation, aggregate results on your side using the `severity`, `risk_score`, and `level` fields returned by each call.

<Info>
**This is intentional.** Many child safety APIs offer session-based context accumulation. We chose not to — because when you're processing messages from minors, the safest data is data you never store. Your integration handles context; Tuteliq handles detection.
</Info>

## Sandbox Mode

API keys with `environment: "sandbox"` run real analysis without consuming credits. Sandbox responses include `"sandbox": true` and the `X-Sandbox-Mode: true` header.

Create a sandbox key in your [Dashboard](https://tuteliq.ai/dashboard) under **Settings > API Keys > Environment: Sandbox**.

Sandbox limits:
- **10 requests per minute** rate limit
- **50 calls per day** (resets at midnight UTC)
- Real analysis, real results — not mocked

<Warning>
Sandbox mode is for integration testing only. Daily limits prevent use as a free production workaround.
</Warning>

## Rate Limits

Rate limits are enforced per API key per minute, based on your plan:

| Plan | Requests/min | Detection credits/mo |
|------|-------------|----------------------|
| Build ($99/mo) | 1,000 | 25,000 |
| Assure ($499/mo) | 5,000 | 150,000 |
| Enterprise | 10,000 | Custom |
| Sandbox | 10 | No credits consumed |

Your allowance is measured in **detection credits**, not requests. Endpoints
are weighted by cost: a text detection is 1 credit, an image 7, a video 95. See
[pricing](https://tuteliq.ai/pricing) for the current plans.

<Note>
Accounts on a legacy plan (Starter, Indie, Pro, Business) keep their existing
limits. Those plans are closed to new signups.
</Note>

Every response includes rate limit headers:

```
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 994
X-RateLimit-Reset: 1710000060
```

When exceeded, the API returns `429 Too Many Requests` with a `Retry-After` header.

## Credits

Each endpoint consumes a different number of credits:

| Endpoint | Credits | Notes |
|----------|---------|-------|
| Text detection (bullying, grooming, unsafe, etc.) | 1 | Per call |
| Grooming / Emotions (with history) | 1 per 10 messages | `ceil(messages / 10)`, minimum 1 |

## Common Error Codes

| Code | HTTP | Description |
|------|------|-------------|
| `AUTH_REQUIRED` | 401 | No API key provided |
| `AUTH_INVALID_KEY` | 401 | API key is invalid or unrecognized |
| `AUTH_EXPIRED_KEY` | 401 | API key has expired |
| `AUTH_INACTIVE_KEY` | 401 | API key is inactive |
| `RATE_LIMIT_EXCEEDED` | 429 | Rate limit exceeded for your tier |
| `MESSAGE_LIMIT_REACHED` | 429 | Monthly credit limit reached |
| `TIER_ACCESS_DENIED` | 403 | Endpoint not available on your tier |
| `VAL_INVALID_INPUT` | 400 | Request body or parameters failed validation |
| `SVC_INTERNAL_ERROR` | 500 | Unexpected internal error (safe to retry) |

For the full error reference and retry strategies, see [Error Handling](/error-handling).
