All Tuteliq API errors return a consistent JSON structure with a machine-readable `code` and a human-readable `message`:

```json
{
  "error": {
    "code": "AUTH_1002",
    "message": "Invalid API key"
  }
}
```

## Error Codes

### Authentication (AUTH_1xxx)

| Code | HTTP | Description |
|------|------|-------------|
| `AUTH_1001` | 401 | API key is required |
| `AUTH_1002` | 401 | Invalid API key |
| `AUTH_1003` | 401 | API key has been revoked |
| `AUTH_1004` | 401 | API key is inactive |
| `AUTH_1005` | 401 | API key has expired |
| `AUTH_1006` | 401 | Unauthorized access |
| `AUTH_1007` | 403 | Access forbidden |
| `AUTH_1008` | 503 | Authentication service unavailable |

### Verification (VERIFY_11xxx)

Age and identity verification return codes in the `VERIFY_11xxx` range. They are also listed, with guidance, on [Age and identity verification](/verification).

| Code | HTTP | Description |
|------|------|-------------|
| `VERIFY_11001` | 500 | Reserved; the API does not currently return it. A document that cannot be read comes back as a verification result with `failure_reasons`, not as an error. |
| `VERIFY_11002` | 400 | No date of birth could be read from the document. Use a document that shows the date of birth clearly. |
| `VERIFY_11003` | 400 | No face was found in the selfie or the document portrait. |
| `VERIFY_11004` | 400 | The face on the document does not match the selfie. |
| `VERIFY_11005` | 400 | The liveness check failed. Take a live photo, not a screenshot or a photo of a photo. |
| `VERIFY_11006` | 404 | Verification session not found. |
| `VERIFY_11007` | 410 | Verification session expired. Create a new session. |
| `VERIFY_11008` | 401 | Invalid session token. Create a new session; do not replay the token. |
| `VERIFY_11009` | 409 | The verification session has already been used. |
| `VERIFY_11010` | 400 | The session is not in the right state for this call, for example already submitted or cancelled. |
| `VERIFY_11011` | 403 | Verification is not enabled for your account, or the configured verification redirect URL does not use `https`. |
| `VERIFY_11012` | 403 | Identity verification requires the Assure plan or above. |
| `VERIFY_11013` | 400 | Reserved; the API does not currently return it. |

### Verification allowance (VERIFY_110xx)

On a plan with a monthly verification allowance, a new verification is checked against
that allowance before any work starts. See
[Verification plans with a monthly allowance](/verification#verification-plans-with-a-monthly-allowance).

| Code | HTTP | Description |
|------|------|-------------|
| `VERIFY_11014` | 402 | The monthly verification allowance, including any purchased verification packs, is used up. Not retryable until the next period starts or more verifications are bought. `details` carries `reason` (`verification_limit_reached`), `period`, `next_period_start`, `included_per_month` and `buy_credits_url`. |
| `VERIFY_11015` | 503 | The allowance could not be checked. Temporary and retryable: the response carries `retryable: true`, `retry_after_ms` and a `Retry-After` header. No verification work was done. |

## Retry Strategy

Not all errors should be retried. Here's a guide:

| Error Type | Retry? | Strategy |
|------------|--------|----------|
| `AUTH_*` | No | Fix your API key or permissions |
| `RATE_2001` | Yes | Wait for the `Retry-After` header value, then retry |
| `VAL_*` | No | Fix the request payload |
| `SVC_4001`, `SVC_4005` | Yes | Exponential backoff, max 3 retries |
| `SVC_4007` | Yes | Wait 5-10 seconds, then retry |
| `NF_*` | No | Check the endpoint URL or resource ID |
| `ANALYSIS_6001`, `6006`, `6007` | Yes | Retry once after a short delay |
| `SUB_7005` | No | Purchase more credits |
| `VERIFY_11002`–`11005` | No | Retake the photo or use a clearer document; retrying the same images gives the same result |
| `VERIFY_11006`–`11010` | No | Create a new verification session |
| `VERIFY_11011`, `VERIFY_11012` | No | Enable verification or fix the redirect URL in the dashboard, or upgrade your plan |
| `VERIFY_11014` | No | Buy more verifications, or wait for `next_period_start` |
| `VERIFY_11015` | Yes | Wait for the `Retry-After` header value, then retry |

### Exponential backoff example

<CodeGroup>
```typescript Node.js
async function withRetry<T>(fn: () => Promise<T>, maxRetries = 3): Promise<T> {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (error instanceof TuteliqError) {
        // Don't retry client errors
        if (error.status < 500 && error.code !== "RATE_2001") throw error;
      }
      if (attempt === maxRetries) throw error;
      const delay = Math.min(1000 * 2 ** attempt, 10000);
      await new Promise((r) => setTimeout(r, delay));
    }
  }
  throw new Error("Unreachable");
}

const result = await withRetry(() =>
  tuteliq.detectUnsafe({ content: "message", context: { ageGroup: "10-12" } })
);
```

```python Python
import time
from tuteliq import Tuteliq, TuteliqError

def with_retry(fn, max_retries=3):
    for attempt in range(max_retries + 1):
        try:
            return fn()
        except TuteliqError as e:
            if e.status < 500 and e.code != "RATE_2001":
                raise
            if attempt == max_retries:
                raise
            delay = min(1 * 2 ** attempt, 10)
            time.sleep(delay)

result = with_retry(
    lambda: client.detect_unsafe(text="message", age_group="10-12")
)
```
</CodeGroup>

<Info>
  The Node.js and Python SDKs have built-in retry logic. Set `retries: 2` (Node.js) or `retries=2` (Python) in the client constructor to enable automatic retries with exponential backoff.
</Info>

## SDK Error Handling

All Tuteliq SDKs throw typed error objects that you can catch and inspect:

<CodeGroup>
```typescript Node.js
import Tuteliq, { TuteliqError } from "@tuteliq/sdk";

try {
  const result = await tuteliq.detectUnsafe({
    text: "some content",
    ageGroup: "10-12",
  });
} catch (error) {
  if (error instanceof TuteliqError) {
    console.error(error.code);    // "AUTH_1002"
    console.error(error.message); // "Invalid API key"
    console.error(error.status);  // 401
  }
}
```

```python Python
from tuteliq import Tuteliq, TuteliqError

try:
    result = client.detect_unsafe(text="some content", age_group="10-12")
except TuteliqError as e:
    print(e.code)     # "AUTH_1002"
    print(e.message)  # "Invalid API key"
    print(e.status)   # 401
```

```swift Swift
do {
    let result = try await tuteliq.detectUnsafe(
        text: "some content",
        ageGroup: .tenToTwelve
    )
} catch let error as TuteliqError {
    print(error.code)    // .authInvalidKey
    print(error.message) // "Invalid API key"
    print(error.status)  // 401
}
```
</CodeGroup>
